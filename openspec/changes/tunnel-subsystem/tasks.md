- [x] 3.2 Implement readiness by local-port probe and failure by child exit / failed probe; tests cover auth failure and forward-bind failure each producing a distinct reason string - `SshTransport::connect` now polls a local TCP dial to the forwarded port (`SSH_READINESS_POLL_INTERVAL`, capped at `SSH_READINESS_PROBE_TIMEOUT` in new `app/src/consts.rs`) instead of a flat sleep, racing it against `try_wait()` on the child each tick; a timeout kills the child and reports a distinct reason. `ssh`'s stderr (now piped instead of discarded) is classified by `classify_exit_failure`: "Permission denied"/"authentication failed" text yields an auth-failure reason, bind-refusal text ("cannot listen", "address already in use", "forwarding request failed", "bind:") yields a bind-failure reason, anything else falls back to the bare exit status. 2 new unit tests assert the two reasons are textually distinct and that unrecognized stderr still produces a sane fallback; the existing local-sshd integration test now exercises the real probe loop (it was previously proven up only by a flat 300ms sleep). 83/83 tests pass (sandboxed run showed unrelated TCP-bind `PermissionDenied` failures in `port_allocator`/`cluster`/`keychain` tests from the Bash sandbox's network restrictions, confirmed absent when run unsandboxed). `cargo fmt`/`cargo clippy` clean on touched files; remaining clippy findings are pre-existing baseline noise in unrelated files. - [x] 3.3 Implement jump-host chains (`-J`); a test through two chained local sshd containers establishes the forward in order - `-J` chain building was already in place from 3.1 (unit test `jump_hosts_produce_a_dash_j_chain` covers arg-list shape); this section adds the integration proof that a chain actually connects. Tracing a real `-J` connection with `-vvv` found that OpenSSH resolves each jump hop via a *separate* `ssh` subprocess (the implicit `ProxyCommand=ssh ... -W %h:%p <hop>` from `ProxyJump`) that re-reads `~/.ssh/config`/`~/.ssh/known_hosts` from the real user's home directory (via the password database, not `$HOME`) rather than inheriting the outer process's `-o` flags - confirmed by first trying a `$HOME` env override, which had no effect, then a `-vvv` trace showing the nested subprocess's own "Reading configuration data" line pointed at the real `~/.ssh/config` regardless. `-F <path>`, unlike `$HOME`, does propagate verbatim to that nested subprocess, so `SshTunnelConfig` gained a new test-only `ssh_config_file` field (`-F`, emitted first in `args()`); production tunnels leave it `None` and rely on the user's real `~/.ssh/config` already trusting their jump hosts. `LocalSshd::spawn` was refactored into `spawn_with_client_key` so a jump instance and a target instance can share one client identity (authorized on both), and gained a `config_via` builder taking explicit `jump_hosts`/`known_hosts`/`ssh_config_file` so the new chain test isn't constrained to the single-hop `config()` shape. The chain test spawns two independent local `sshd` instances (jump + target), writes a scratch `-F` config aliasing the jump hop (`Host jumphop`) to the shared key/known_hosts, connects through `target.config_via(&["jumphop".into()], ...)`, and proves the forward still proxies a real TCP echo end to end - same as the 3.1 single-hop test, just with the extra hop in the way. 84/84 tests pass unsandboxed (both sshd integration tests skip, not fail, under the Bash sandbox's spawn restrictions - confirmed absent when run unsandboxed). `cargo fmt`/`cargo clippy --all-targets -- -D warnings` clean on `ssh_tunnel.rs`; remaining clippy findings are the same pre-existing baseline noise in unrelated files noted in 3.2
- [x] 3.4 Implement child-process cleanup: process-group kill on drop and a startup sweep for orphaned forwards from a stale pid file; a test kills the supervisor and asserts no `ssh` child survives - `ssh` now spawns with `process_group(0)` (unix-only) so a `-J` jump-host hop, which runs as a separate `ssh` subprocess inheriting the outer process's group rather than detaching, dies alongside it instead of surviving `kill_on_drop` (which only signals the direct pid). New `app/src/pidfile.rs`: `PidFile::write`/`Drop` tracks one pidfile per live forward in `paths::cache_dir()/ssh-pids/`, `kill_process_group`/`process_group_alive` shell out to `kill`/`kill -0` against `-pid` (killpg via subprocess rather than adding a `libc` dependency for one syscall), and `sweep_stale` kills and removes whatever pidfiles are found at startup - any that exist are necessarily orphans, since a clean `Drop` always removes its own. `SshTransport` gained a manual `Drop` that calls `kill_process_group` on the recorded child pid and lets the pidfile's own `Drop` clean up; `connect()` writes the pidfile right after spawn and clears it on every exit path (timeout, check failure, ssh exiting on its own). The required test - `dropping_the_transport_kills_the_whole_process_group_including_the_jump_hop` in `sshd_integration.rs` - establishes a forward through a real jump-host chain (same throwaway two-sshd setup as 3.3), confirms via `pgrep -g <pid>` that the group has live members (the direct `ssh` plus its `-J` hop subprocess), drops the transport, and confirms `pgrep -g <pid>` finds nobody left. 4 new `pidfile.rs` unit tests cover `kill_process_group` against a real process, a stale-pidfile sweep killing and removing it, sweep ignoring non-`.pid` files/empty dirs, and `PidFile::write`+`Drop` round-tripping the file. 89/89 tests pass unsandboxed (all three sshd-dependent tests skip, not fail, under the Bash sandbox's spawn restrictions - confirmed passing when run unsandboxed). `cargo fmt`/`cargo clippy --all-targets -- -D warnings` clean on every touched file; the 24 remaining clippy errors are the same pre-existing baseline noise (`logs.rs`, `pods.rs`, etc.) noted in 3.2/3.3, confirmed unchanged by stashing this change and re-running clippy. ## 4. Kubernetes port-forward implementation

- [x] 4.1 Implement `K8sPortForward`: local `TcpListener` on the allocated port, each connection bridged to a fresh `kube` port-forward stream; a test against a mock/kind cluster forwards to a Service port and serves a request - no `kind`/Docker on this machine (same constraint as section 3), so `app/src/k8s_port_forward.rs` is tested against a hand-rolled fake API server instead: plain HTTP/1.1 over a real local `TcpListener` that answers a `Pod` GET and performs the WebSocket upgrade `kube`'s portforward subresource expects (`kube`'s `ws` feature enabled), then speaks its binary channel-multiplexed wire protocol well enough to echo whatever the "forwarded port" receives. `PodPortForwardTransport` implements section 2.3's `ForwardTransport`: unlike `SshTransport`, there's no persistent child process to supervise, so `connect`/`health_check` both mean "the Pod exists and is `Running`" via `Api::<Pod>::get`. The actual data path is `serve`, an accept loop that bridges each incoming local connection to its own fresh `Api::<Pod>::portforward` call with `copy_bidirectional` - `kube`'s `Portforwarder` multiplexes by port, not by client connection, so (unlike `ssh -L`, which shares one child across every local connection) there's no connection sharing to do. Debugging note worth keeping: the fake server's request-header parser first lowercased the whole request for case-insensitive header-name matching, which corrupted `Sec-WebSocket-Key`'s value (base64, case-sensitive) and produced a "Sec-WebSocket-Accept key mismatched" failure - fixed by keeping header text as-is and matching only the header *name* case-insensitively. 92/92 tests pass unsandboxed (bind-related tests, including this section's, fail under the Bash sandbox's TCP restrictions and pass unsandboxed, consistent with prior sections). `cargo fmt`/`cargo clippy --all-targets -- -D warnings` clean on every touched file; 23 remaining clippy errors are the same pre-existing baseline noise noted in 3.2-3.4.
