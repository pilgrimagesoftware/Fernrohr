Fixed by adding kube's `aws-lc-rs` feature so `ClientBuilder::try_from` self-installs (`kube-client-4.2.0/src/client/builder.rs:122`); this is a `bootstrap-fernrohr` `cluster-connection` gap, not tunnel-subsystem-specific, but it blocks section 5 either way

## 2. ManagedForward core

- [x] 2.1 Define `ForwardState` (Disconnected/Connecting/Up/Reconnecting) and the `ManagedForward` trait (`state()` receiver, `local_addr()`, handle-based acquire/release); unit tests drive a fake implementation through every transition - `app/src/managed_forward.rs`: `state()` returns a `tokio::sync::watch::Receiver<ForwardState>`; `acquire()` returns a `ForwardHandle` whose `Drop` runs a release callback. 4 tests against a `FakeForward` cover every state transition, `local_addr()`, and acquire/drop refcounting (single and two independent handles). `SshTunnel`/`K8sPortForward` (sections 3-4) are the first real implementations - marked `UNWIRED`
- [x] 2.2 Implement the local-port allocator (bind `127.0.0.1:0`, hand back the port; honor an explicit port and report conflicts); tests cover auto-allocation and explicit-port-in-use - `app/src/port_allocator.rs`: `allocate()`/`allocate_explicit(port)` return an `AllocatedPort` holding the live `TcpListener` (not just the port number) so there's no gap between reservation and use. 4 tests: auto-allocation is on 127.0.0.1 with a nonzero port, two auto-allocations differ, an explicit port is honored, and re-requesting a held port surfaces `io::ErrorKind::AddrInUse`. Marked `UNWIRED` - the section 2.3 supervisor is the first caller
- [x] 2.3 Implement the per-forward supervisor task: owns the state machine, runs a health-check tick, and applies backoff on failure; tests with a fake transport cover transient-drop recovery keeping the same port and sustained-failure staying in Reconnecting - `app/src/forward_supervisor.rs`: `ForwardTransport` trait (`connect`/`health_check`, RPITIT) is what `SshTunnel`/`K8sPortForward` plug in; `ForwardSupervisor::spawn` owns a tokio task driving Connecting/Reconnecting -> connect -> Up -> periodic health-check, aborting the task on `Drop` per the owning-spawned-work convention. `BackoffPolicy` doubles per consecutive failure since the last `Up`, capped at `max`. 2 tests against a scripted fake transport: a transient health-check failure recovers to `Up` with `local_addr()` unchanged, and sustained connect failures stay in `Reconnecting` (never regress to `Disconnected`) rather than giving up. Found and fixed a real race while writing the second test: a fake transport with no genuine await point lets a whole Reconnecting->Up cycle resolve within one scheduler turn, invisible to a concurrently polling `watch::Receiver` - the fix (`tokio::task::yield_now()` in the fake) documents that any real transport must have a genuine await point for intermediate states to be observable, which `ssh`/`kube` I/O naturally provides. Marked `UNWIRED`
- [x] 2.4 Implement `ForwardRegistry` (app-scoped) with identity keying and reference counting; tests assert one underlying forward for two acquirers and teardown on last release - `app/src/forward_registry.rs`: `Weak`-based cache keyed by identity string; `acquire(identity, factory)` upgrades the cached `Weak` if live, else runs `factory` and caches a fresh `Weak`. `RegistryHandle` holds the `Arc<F>` plus the `ManagedForward::acquire()` handle from section 2.1, so dropping the last handle for an identity drops the `Arc` to zero and the forward tears itself down via its own `Drop` - no separate registry-side cleanup pass needed. 4 tests against a `CountingForward` fake: two acquirers of one identity share a forward (factory runs once, same `Arc`), different identities get independent forwards, teardown fires only after the last of two handles drops, and a fresh acquire after teardown builds a new instance rather than reusing the stale one. Marked `UNWIRED`; section 6.2's connect-path integration is the first real caller
